# 中文检索踩坑记录

> 这份文档记录的是：**从"能搜到"到"搜得准"的全过程，以及每一步的实测数据。**
> 写简历、准备面试时可以直接翻这里——它比"我做了 RAG"这种描述具体得多。

---

## 背景

RAG 的第一环是"检索"：用户提问，系统从知识库里找出最相关的几段文档，交给模型回答。

检索做不准，后面全白搭——**模型再强，你给它的资料是错的，它也只能答错或编造。**

我们用的是 PostgreSQL 的全文检索（词法通道）。它是英文优先设计的，
所以中文上连踩四个坑。下面每个坑都附了**可复现的验证命令**。

---

## 坑 1：PostgreSQL 默认不切中文（整句变成一个词）

### 现象

```sql
SELECT to_tsvector('simple', '星澜科技的边缘计算网关');
-- 结果：'星澜科技的边缘计算网关':1        ← 整句被当成【一个词】

SELECT to_tsvector('simple', '星澜科技的边缘计算网关')
       @@ to_tsquery('simple', '边缘计算');
-- 结果：f（false）—— 搜不到，永远搜不到
```

### 原因

PostgreSQL 的 `simple` 分词配置按**空格和标点**切词。中文没有空格，所以整句成了 token。

### 关键细节：光在入库时切没用，查询侧也必须切

```sql
-- 即使入库时切好了：
SELECT to_tsvector('simple', '星澜科技 的 边缘 计算 网关')
       @@ plainto_tsquery('simple', '边缘计算');
-- 结果：f —— 因为 plainto_tsquery 把「边缘计算」也当成一个整词
```

### 解决

**两侧都用 jieba 分词：**

```sql
-- 入库：Python 侧用 jieba 切好、空格连接，写进 content_seg
-- 查询：Python 侧切好后拼成带 & 的 tsquery
SELECT to_tsvector('simple', '星澜科技 的 边缘 计算 网关')
       @@ to_tsquery('simple', '边缘 & 计算');
-- 结果：t ✅
```

### 工程实现

| 位置 | 做法 |
|---|---|
| 表结构 | `content` 存原文；`content_seg` 存分词结果（空格连接）；`tsv` 从 `content_seg` 生成 |
| `tsv` 为什么用生成列 | `to_tsvector(regconfig, text)` 两参数版本是 immutable，可以做 `GENERATED ALWAYS AS ... STORED` |
| 索引 | `GIN(tsv)` —— 建在 `content` 上的话，中文检索等于没有索引 |

> ⚠️ 这个坑在 SQLite 的 FTS5 上**完全一样**（默认 `unicode61` 分词器同样不切中文，
> 实测查询命中数为 0）。**所有"默认只服务英文"的全文检索方案，碰到中文都会这样。**
> SQLite 的解法是 `tokenize='trigram'`。

## 坑 2：分词粒度不匹配（库里存「无锡市」，用户查「无锡」）

### 现象

```sql
-- 库里存的是 token「无锡市」
SELECT tsv FROM chunks WHERE content LIKE '%无锡%';
-- '无锡市':10 ...

SELECT count(*) FROM chunks WHERE tsv @@ to_tsquery('simple', '无锡');
-- 结果：0 ❌ 搜不到
SELECT count(*) FROM chunks WHERE tsv @@ to_tsquery('simple', '无锡市');
-- 结果：1 ✅
```

### 原因

PostgreSQL 全文检索是**精确词匹配**。`无锡` ≠ `无锡市`。

### 解决：查询侧用 `cut_for_search`

```python
jieba.cut("无锡市在哪里")            → ["无锡市", "在", "哪里"]
jieba.cut_for_search("无锡市在哪里") → ["无锡", "无锡市", "在", "哪里"]   ✅
```

`cut_for_search`（搜索引擎模式）会把长词**再切细一遍**，正好补上粒度差。

**代价**：查询词变多，会引入噪音，需要靠排序（BM25 的 IDF）压住。这是"召回"和"精确"之间的经典取舍。

**另一条保险**：给查询词加前缀匹配，`to_tsquery('simple', '无锡:*')` 也能命中 `无锡市`。

## 坑 3：分词错误（「林澈」被吞进错误的长词里）

### 现象

```
原文：边缘计算业务线由林澈负责，他于 2019 年 4 月加入星澜科技，毕业于浙江大学...
jieba 默认切成：业务 | 线由林澈 | 负责
                        ↑↑↑↑↑↑
                  「林澈」被吞进了一个不存在的词里
```

查询「林澈」**永远匹配不到这一块**。

### 这个坑为什么特别危险

因为它**会被偶然掩盖**。同一篇语料里如果另有一句"边缘计算业务线负责人是林澈"恰好切对了，
查询就能命中，你会以为一切正常——**但真正需要的那一块（含学历信息的那块）被静默漏掉了。**

漏掉的恰好是多跳题要用的那块："澜芯 X1 由哪个团队开发？负责人毕业于哪所大学？"

### 解决：自定义领域词典

```python
jieba.add_word("林澈")

# 实测：
#   默认      : 业务 线由林澈 负责      ❌
#   加词典后  : 业务 线 由 林澈 负责    ✅
```

**维护一个领域词典**（人名、产品名、型号），入库前加载。
中文人名绝大多数是 2 字，恰恰是 jieba 最容易切错的一类。

## 坑 4：pg_trgm 对中文短词完全无效

我们原本建了 `GIN(content gin_trgm_ops)` 想当兜底通道。**实测完全没用。**

### 实测数据

| 查询词 | 长度 | `similarity(q, content)` 最大值 | `word_similarity(q, content)` 最大值 |
|---|---|---|---|
| `无锡` | 2 字 | **0.0000** | **0.0000** |
| `边缘计算` | 4 字 | 0.0400 | 0.8000 |

### 原因

pg_trgm 会给字符串**两端补空格**再切三元组：

```
'无锡' 补成 '  无锡  '  →  三元组：{"  无", " 无锡", "无锡 ", "锡  "}
正文中截取的片段 '无锡市' →  三元组：{"无锡市"}
交集 = 0        ← 带空格的三元组在正文里根本不存在
```

**词越短，补空格造成的"污染"占比越高。** 中文人名、地名绝大多数是 2~3 字，
所以这个方案对中文基本不可用。

> **结论**：trigram 索引可以留着（对长词的模糊匹配有点用），但**不能当作中文检索的兜底方案**。
> 而且 `%` 操作符用的是 `similarity`（整串比较），方向就不对；要比较子串应该用 `<%`（`word_similarity`）。

## 汇总

| # | 问题 | 影响 | 解决 | 状态 |
|---|---|---|---|---|
| 1 | PostgreSQL 默认不切中文 | 中文检索完全失效 | 两侧 jieba 预分词 + `content_seg` 列 + `GIN(tsv)` | ✅ 已解决 |
| 2 | 分词粒度不匹配 | 短查询词漏检 | 查询侧 `cut_for_search` + 前缀匹配 `:*` | ✅ 已解决 |
| 3 | 分词错误 | 专有名词静默漏检 | 领域自定义词典 `jieba.add_word` | ✅ 已解决 |
| 4 | pg_trgm 对短词无效 | 没有兜底通道 | 无词法手段可解 | ⚠️ **留给向量检索** |

### 修复前后的效果

| 查询 | 修复前 | 修复后 |
|---|---|---|
| `边缘 & 计算` | **0** | 6 |
| `无锡` | 0 | 1（靠 `cut_for_search` 切出「无锡」） |
| `林澈`（含学历的那一块） | 0 | 1（靠自定义词典） |
| `量子 & 计算机`（负例） | 0 | 0 ✅ 不误命中 |

## 仍未解决问题的意义

**坑 1~3 是"实现细节没做好"，坑 4 是"方案本身的边界"。**

坑 4 说明了一件事：**纯词法检索在中文上有无法靠调参解决的天花板。**
两个说法不同的句子，只要用词不同，词法检索就找不到——这是词法方法论的固有局限，不是 bug。

**这正是要做向量检索的动机，也是"混合检索"这个方案存在的理由：**

```
词法通道（BM25）  → 擅长专有名词、编号、型号，精确匹配
向量通道（embedding）→ 擅长语义相近但用词不同的情况
                     两者融合（RRF），各补各的短板
```

**而"我知道我的词法通道在哪里会失效、失效多少"，
恰恰是做混合检索和消融实验的前提**——否则你无法证明向量通道到底带来了多少收益。

## 第二阶段：BM25 检索的实测发现

修完上面四个坑之后，词法检索基本可用了。实测 5 个问题，4 个排第一命中正确：

| 问题 | 第 1 名命中的块 | 结果 |
|---|---|---|
| 无锡市在哪里 | 块 30（含"位于江苏省无锡市"） | ✅ |
| **林澈毕业于哪所大学** | **块 27（含"毕业于浙江大学"）** | ✅ **坑 3 的最终验收** |
| 澜芯 X1 是什么时候发布的 | 块 28（产品线） | ✅ |
| 企业版 SLA 承诺多少可用性 | 块 31（服务与定价，得分 9.743） | ✅ |
| 量子计算机有什么进展 | 块 27（**错误命中**） | ❌ |

**但剩下那一个错误，暴露了两个新问题。**

---

### 新问题 5：`cut_for_search` 引入噪音（修复坑 2 的代价）

```
【问】量子计算机有什么进展
  查询分词：['量子', '算机', '计算机', '计算', '有', '什么', '进展']
                              ↑↑↑↑
  1. 得分 2.728  [块27] 核心团队     ← 错误命中

原因：语料里有"边缘【计算】业务线"，
      cut_for_search 把「计算机」切出了「计算」，正好命中。
```

**这个错误命中的得分（2.728），甚至比"无锡市在哪里"的正确命中（1.734）还高。**

这就印证了前面说的代价：**搜索模式切出的细粒度词能提高召回，但同时引入噪音。**
而且 **`有`、`什么` 这类常见词也在贡献分数**——IDF 压低了它们，但没有压到 0。

### 新问题 6：长块优势

块 30（合作伙伴文档）在三个查询里都进了前 3：

| 查询 | 块 30 的排名 |
|---|---|
| 无锡市在哪里 | 第 1 名（正确） |
| 林澈毕业于哪所大学 | 第 2 名（2.422） |
| 澜芯 X1 是什么时候发布的 | 第 2 名（3.714） |

**原因**：这篇文档最长、含词最多，任何查询都能在里面碰上几个词。
BM25 的长度归一化（`b=0.75`）会打折，但**打折的力度不足以抵消"词多"的优势**。

---

### 这两个问题的意义

它们和坑 4 是同一个层次的发现——**不是实现细节没做好，而是词法方法论的边界**：

| 问题 | 词法手段能解决吗 |
|---|---|
| 坑 4：语义相近但用词不同 | ❌ 不能，这是词法的根本局限 |
| 新问题 5：细粒度分词引入噪音 | ⚠️ 只能靠调参缓解，无法根治 |
| 新问题 6：长块优势 | ⚠️ 同上 |

**这三条加起来，构成了做「混合检索 + 精排」的完整动机：**

```
第 1 层  词法召回（BM25）   → 快，擅长专有名词/型号/编号，但会漏语义、会引入噪音
第 2 层  向量召回（embedding）→ 擅长语义相近，补上词法漏掉的那部分
第 3 层  融合（RRF）        → 两个通道的结果合并
第 4 层  精排（reranker）    → 对候选集重新打分，把"恰好含有一个词"的假命中压下去
```

**每一步都有实测数据支撑，而不是"因为别人都这么做"。**
这是这套笔记最值钱的地方——面试问"你为什么做混合检索"，你可以直接报数字。

# 第三阶段：换上真实语料之后

## 为什么要换语料

前两个阶段用的是一份 **5 篇文档 / 8 个片段** 的虚构演示语料。
它足够验证链路，但**不足以证明任何东西**：

| | 演示语料 | 真实语料（Vue 3 官方中文文档） |
|---|---|---|
| 文件数 | 5 | **68** |
| 字符数 | 1,914 | **453,930** |
| 切块后片段数 | 8 | **1,919** |
| `top_k=3` 覆盖率 | **38%** | **0.26%** |

**`top_k=3` 覆盖 38% 的语料时，正确率 100% 是虚高的**——检索几乎不可能失败，
这个数字说明不了系统的能力。报告里必须写清样本量，否则就是自欺欺人。

> 顺带一提：语料换成递归目录结构后，`doc_id` 由**相对路径**派生，
> 所以 `guide/components/slots.md` 和 `guide/essentials/...` 不会撞车。
> 如果扁平复制，Vue 文档里有重名文件（`description.md`），会互相覆盖。

---

## 真实规模下暴露的问题：负例得分和正例无法区分

在 1,919 个片段上测 6 个问题，其中一个是**语料里根本不存在的负例**：

| 问题 | 第 1 名命中 | 判定 |
|---|---|---|
| Vue 3 的响应式原理 | "深入研究 Vue 响应性系统的一些底层细节" | ✅ |
| 怎么注册一个全局组件 | 组件注册（全局 / 局部） | ✅ |
| 什么是组合式 API | "为什么要有组合式 API" | ✅ |
| computed 和 watch 有什么区别 | watchEffect 与 watch 的区别 | 🟡 相关但非最佳 |
| props 可以被子组件修改吗 | v-model 双向绑定 | 🟡 部分相关 |
| **量子计算机有什么进展**（负例） | 关于缓存的一段，**得分 8.670** | ❌ **误命中** |

**关键数字：**

```
负例「量子计算机」的最高分      = 8.670
「props 能否被修改」的第 2 名   = 8.886
                                  ↑ 几乎一样
```

**分数区间重叠了。纯 BM25 分不清"真相关"和"恰好含高频词"。**

原因很具体：Vue 文档里 `computed` 的中文叫「**计算**属性」，
"计算"是超高频词；而"量子**计算**机"里的"计算"正好撞上。

**这就是「新问题 5：`cut_for_search` 引入噪音」在真实规模下的放大版**——
在 8 个片段的玩具语料上只是"偶尔误命中"，到 1,919 个片段就变成"分数不可区分"。

### 这个数据怎么用

面试被问"你为什么做混合检索 / 为什么要加 rerank"，可以直接报：

> "我的纯词法通道在负例上的最高分是 8.67，而正例第 2 名是 8.89，
> 两个区间重叠，**单靠 BM25 无法做拒绝判断**。所以需要向量通道补充语义召回，
> 再用 reranker 对候选集重新打分。"

**这比"因为大家都这么做"强得多。**

---

## 语料换了之后必须做的事

| 要做的事 | 原因 |
|---|---|
| **清空数据库再入库** | 否则旧语料的文档会残留，检索时串进来 |
| **重新生成评测集** | 评测集的 `doc_id` 绑定旧语料，`eval.validate` 会报 `unknown_doc` |
| **重启后端** | `app/bm25.py` 的索引是进程内缓存的，不重启会一直用旧索引 |

```powershell
cd E:\Vue\Agent
docker exec agent-rag-pg psql -U agent -d agent_rag -c "TRUNCATE documents CASCADE;"
docker compose up -d
cd backend
.venv\Scripts\python -m app.ingest
```

> **`eval.validate` 报 `unknown_doc` 是好事**——它是专门用来抓"语料换了但评测集没换"
> 这类静默失效的。没有这个校验，你会拿着作废的评测集跑出毫无意义的数字。

# 第四阶段：模型缓存被系统清理（排查了很久的一个坑）

## 症状：完全没有指向性的报错

某次重启后端，健康检查一直超时。翻后端日志才看到：

```
Fetching 6 files:  83%|████████▎ | 5/6 [00:23<00:06]     ← 在重新下载模型！
```

一查缓存目录：

```
=== blobs（实际文件）===
        0.0 MB  ...incomplete
=== 总大小 ===
  14.7 MB          ← 2.4GB 的模型没了，只剩下 tokenizer
```

## 根因：`fastembed` 默认把模型下载到 `%TEMP%`

```
C:\Users\Administrator\AppData\Local\Temp\fastembed_cache\
                    ↑ Windows 会清理临时目录
```

**这一个原因解释了之前反复出现的所有怪现象**：

| 之前看到的现象 | 我当时以为的原因 | 真实原因 |
|---|---|---|
| "下载卡死，60 秒零增长" | 镜像站不稳定 | 缓存被清，在重下 |
| "后端启动慢、健康检查超时" | 机器性能问题 | 启动时在重下模型 |
| "入库花了 766 秒" | 模型太大 | （这次确实是模型大，但同类现象会混淆） |

**没有任何一行报错指向真正的原因**——症状是"请求超时"，不是"文件不存在"。

## 修法

```python
# app/embedding.py
# fastembed 默认把模型下载到 %TEMP%，而 Windows 会清理临时目录。
CACHE_DIR = Path(__file__).resolve().parent.parent / ".models"
CACHE_DIR.mkdir(parents=True, exist_ok=True)

def get_model():
    return TextEmbedding(EMBEDDING_MODEL, cache_dir=str(CACHE_DIR))
```

并把 `backend/.models/` 加进 `.gitignore`（2.4GB 不入版本库）。

## 教训

> **凡是"下载很慢""偶尔失败""重启后又要下载"这类不稳定现象，
> 先问一句：文件到底存在哪？那个地方会被清理吗？**

`%TEMP%` 是最容易被忽略的地方 —— 程序跑起来没问题，直到某次系统清理。

# 第五阶段：延迟归因（测量推翻了优化方向）

## 先埋点，不要猜

原来 `retrieve.agent.compress` 是一个 5.5 秒的黑盒。加了子 span 之后才看清：

```
端到端 P50 = 4692 ms

retrieve.agent.compress   3695 ms   ← 父 span（包含下列全部）
  ├─ compress.context     1565 ms    33.4%   ← 最大单项
  ├─ planner.assess        964 ms    20.5%
  ├─ planner.decompose     780 ms    16.6%
  └─ retrieve.round1       474 ms    10.1%   ← 检索（含向量化）
llm.stream                 986 ms    21.0%   ← 最终生成
```

**71% 的时间花在三次辅助 LLM 调用上，检索只占 10%。**

我原本的计划是"并行化多路检索"——**那只动得到 10%。**
如果没先测，会改一堆代码然后发现没效果。

## 换更快的模型？行不通

查了一下可用的模型：

| 模型 | 压缩提示词下的 P50 | 返回内容 |
|---|---|---|
| `deepseek-chat` | **1340 ms** | **3/3** ✅ |
| `deepseek-flash` | 8743 ms | **0/3** ❌ |
| `deepseek-v4-pro` | 23404 ms | **0/3** ❌ |

后两个是**推理模型**（内容都在 `reasoning_content` 字段里），
对这个任务慢 6~17 倍。**"用快模型做辅助任务"这条路在当前 provider 下不可行。**

## 批量向量化：2 倍，省 1.3 秒

查询分解会产生 2~4 个子查询。之前每个子查询各调一次 `embed_query`，
就是 N 次独立的 ONNX 推理。改成一次批量：

```
检索层耗时（4 路查询，各取 top10 候选，中位数 5 轮）

逐个 hybrid.search        :  2692 ms
批量 hybrid.search_many   :  1377 ms    → 1.96x，省 1315 ms

向量化 逐个 × 4           :  2401 ms
向量化 批量               :  1063 ms    → 2.26x，省 1337 ms
```

**正确性验证（性能优化不能改结果）**：

```
逐个 vs 批量，逐路比较 chunk_id 序列一致: True
完整评测跑一遍：救回 5 / 弄丢 6，p = 1.0000（不显著）
```

## 顺带踩到的两个测量陷阱

**陷阱 1：`fastembed` 的 `query_embed` 返回生成器（惰性求值）**

```python
[m.query_embed([q]) for q in qs]     # 耗时 0 ms —— 因为根本没执行！
list(m.query_embed(qs))              # 这才真正跑
```

不迭代它就什么都不做。第一次测量就栽在这里，得出"逐个调用 0ms"的荒谬结果。

**陷阱 2：这台机器上跑不了两个进程同时加载模型**

```
内存总计 15.6 GB，可用 6.4 GB
模型 2.3 GB / 份
```

后端进程 + 独立基准进程各加载一份模型 → 内存吃紧 → 换页 → **ONNX 推理掉到 1/4**。

同一个批量调用，早先测 231 ms，后来测 879 ms —— **同一个操作差 3.8 倍**。

> **教训：绝对延迟数字必须注明测量环境。**
> 相对比较（同一次运行内的 A/B）才可靠；
> 跨运行、跨机器比绝对毫秒数没有意义。
