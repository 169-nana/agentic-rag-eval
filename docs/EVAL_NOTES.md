# 评测踩坑记录

> 这份文档记录的是**「怎么把 RAG 的效果量化出来」**，以及过程中踩的坑。
> 和 `RETRIEVAL_NOTES.md`（讲检索本身）配套阅读。
>
> 这里记的是**"我怎么证明它变好了"**——比"我做了什么"更能体现工程成熟度。

## 一、三条设计决定

### 决定 1：标准答案用「原文片段」，不绑 chunk id

```python
@dataclass
class GoldSpan:
    doc_id: str
    text: str        # 文档中逐字出现的原文片段
```

**为什么？** 因为后面要做「分块策略消融实验」——对比固定切分 / 语义分块 / 父子块。
如果标准答案绑的是 chunk id，每换一种分块就得重新标注一遍评测集，**实验根本做不下去**。

改成绑原文片段之后，检索是否命中通过**文本覆盖度**判定（`eval/text.py: is_covered`），
同一份评测集可以评测任意分块策略。

### 决定 2：三类题，三种验证方式

| 类型 | 生成方式 | 关键验证（防止指标失真） |
|---|---|---|
| 单跳 | 针对单个片段出事实题 | evidence 必须能**定位回原文**，否则丢弃 |
| 多跳 | 实体共现索引 → 跨文档片段对 → 桥接题 | evidence 两条都要能定位 + **两道额外校验**（见坑 3） |
| 不可回答 | 把真实问题里的实体替换成"合理但语料中不存在"的实体 | 替换后的实体必须**确实不在**语料里 |

最后一条是幻觉率能否成立的前提：如果替换出的实体碰巧语料里有，
这道题就变成可回答的了，**幻觉率会虚高**。

### 决定 3：评测器自己要先被验证

`--system oracle` 直接返回标准答案。**喂标准答案，各项指标必须接近满分。**

```
如果 oracle 跑不出 1.0 → 是判分器或指标写错了，不是被测系统的问题
```

> **一个没被验证过的评测器比没有评测器更危险**，因为它会给你虚假的信心。

## 二、坑 1：两个指标数据源不一致，跑出自相矛盾的数字

### 现象

第一次跑基线，报告里同时出现：

```
拒答正确率  0.6667
幻觉率      1.0        ← 这两项按定义应该互为 1 - 对方
```

### 原因

| 指标 | 当时用的数据源 |
|---|---|
| `refusal_accuracy` | LLM judge 的判定 |
| `hallucination_rate` | `detect_refusal()` **关键词匹配** |

模型实际说的是：

```
「我目前没有"星澜科技"2023 年营业收入的数据。」     ← 合格的拒答
「我无法确认星澜科技是否在深圳设有研发中心。」       ← 合格的拒答
```

关键词表（"资料不足 / 无法回答 / 未提及"……）**一个都没覆盖到**，于是全判成"没拒答"。

### 修法

两项都改成取自 judge 的判定，互为 `1 - 对方`。

```python
"refusal_accuracy":   _mean_bool([r.verdict.correct     for r in unanswerable]),
"hallucination_rate": _mean_bool([not r.verdict.correct for r in unanswerable]),
```

**顺带把关键词表补全了，但它的定位降级为"粗略标记"，不再参与任何指标计算。**

### 教训

> **当两个指标互相矛盾时，一定是定义错了，不是系统表现奇怪。**

## 三、坑 2：模型有随机性，单次评测不可靠

### 现象

基线跑了两次，**同一道题的判分从 0.6667 变成 1.0**。去对比原始回答：

| 次数 | 对「澜芯 X3 网关的发布时间」的回答 |
|---|---|
| 第 1 次 | 「澜芯 X3 网关的发布时间是 **2023年5月**。」 ← **编造** |
| 第 2 次 | 「具体发布时间我无法确认，建议查阅官方公告。」 ← 正确拒答 |

**同一道题、同一个系统、同一个模型，两次回答完全不同。**（temperature = 0.3）

### 结论

| 结论 | 可信度 |
|---|---|
| 可回答题正确率 0.0 → 1.0 | ✅ 可信（两次都是 0.0 / 1.0，13 题全错 vs 全对，差异足够大） |
| 幻觉率 0.0 | ⚠️ **不可信**（只有 3 道不可回答题，模型行为本身就随机） |

**3 个样本里只要有一次编造，幻觉率就变成 0.33。**

### 应对

1. **把不可回答题从 3 条扩到 20 条** ← 最优先
2. 跑多次取平均，或报告波动范围
3. 报告里必须写明样本量

## 四、坑 3：合成的多跳题有三类废题

第一版生成器（实体共现配对 + 出题）产出的多跳题，**3 条里 2 条是废的**。

### 废题类型 1：张冠李戴

```
问：澜芯 X2 边缘计算网关由哪位负责人领导的团队主导开发？
答：林澈
gold 片段 1：边缘计算业务线由林澈负责
gold 片段 2：它由边缘计算团队主导开发
             ↑ 原文里这个「它」指的是【澜芯 X1】，不是 X2
```

### 废题类型 2：并列式（伪装成桥接）

```
问：澜芯 X2 搭载的芯片由哪家公司提供，该公司的企业版客户享有哪项专属支持？
```

两个问句之间**没有任何推理关系**，拆成两道单跳题各答各的就行。
而且"该公司的企业版客户"逻辑本身就是错的——那是星澜科技的服务，不是芯片供应商的。

### 废题类型 3：伪多跳

```
问：星澜科技与哪家位于无锡的芯片设计公司联合开发了 HC-300 芯片？
```

第一段原文已经写了"恒远半导体的 HC-300"，**只看一段就能答**。
而且问题里"位于无锡"直接把答案提示出来了。

### 修法 A：加两道自动校验

| 校验 | 怎么问模型 | 抓哪类废题 |
|---|---|---|
| **可解答性** | 把问题 + 答案 + 两段原文给它，问"这个答案能从这两段推出来吗" | 张冠李戴 |
| **必要性** | 分别只给一段，问"只看这一段能回答吗" | 伪多跳 |
| （原本就有）证据定位 | evidence 必须能逐字定位回原文 | 胡编的依据 |

### 修法 B：提示词给正反例

光加校验不够——校验是"事后过滤"，提示词是"事前预防"。
在 `MULTI_HOP_PROMPT` 里明确写出：

```
✅ 好例子：「星澜科技负责边缘计算业务线的负责人是谁？他主导开发的产品搭载了哪家公司的芯片？」
   推理链：第一段得到"林澈/边缘计算团队" → 拿这个结果去第二段找芯片供应商

❌ 坏例子：「澜芯 X2 用哪家公司的芯片？企业版客户的支持由哪个团队对接？」
   —— 两个问句之间没有任何推理关系，拆成两道单跳题各答各的就行
```

### 效果

| 版本 | 结果 |
|---|---|
| 改进前 | 3 条多跳题里 **2 条逻辑错误、1 条伪多跳** |
| 加校验后 | 10 个候选里 **3 条判为伪多跳被丢弃** |
| 加校验 + 改提示词后 | 10 个候选 → 3 条丢弃 → 7 条留下，质量从"并列式"变成"桥接式" |

> **这套三道校验 + 正反例提示词，本身就是值得单独展开讲的工程细节。**

## 五、坑 4：语料规模决定了题量上限

```
语料：5 篇文档 → 5 个片段

单跳题上限 = 片段数             = 5
多跳题上限 = 跨文档实体片段对数   = 10
不可回答上限 = 单跳题数          = 5
────────────────────────────────────
合计上限约 20 道
```

**想生成 100 道题，语料得大 5~10 倍。** 换了真实语料之后：

| | 演示语料 | Vue 3 官方中文文档 |
|---|---|---|
| 文件数 | 5 | 68 |
| 字符数 | 1,914 | 453,930 |
| 片段数 | 8 | 1,919 |
| `top_k=5` 覆盖率 | 38%（闭眼都能中） | **0.26%（真实难度）** |

**`top_k=3` 覆盖 38% 的语料时，100% 正确率是虚高的** —— 必须换语料才有说服力。

两组跑的是同一套题、同一个模型、同一个判分器，**唯一差别是"有没有检索"**

## 七、真实规模的数字（98 条题 / 1,919 个片段）

语料：Vue 3 官方中文文档（68 篇）
评测集：98 条（50 单跳 / 30 多跳 / 18 不可回答，模型合成 + 三道校验）
判分器：LLM judge

| 指标 | 纯 LLM（无检索） | **RAG（BM25 检索 + 生成）** |
|---|---|---|
| 可回答题正确率 | 0.6125 | 0.6000 |
| **拒答正确率** | **0.0** | **0.9444** |
| **幻觉率** | **1.0** | **0.0556** |
| 片段召回率@5 | 0.0 | 0.7125 |
| 命中率@5 | 0.0 | 0.8250 |
| MRR | 0.0 | 0.7188 |
| nDCG@5 | 0.0 | 0.7270 |
| 延迟 P50 / P95 (ms) | 813 / 1402 | 864 / 1316 |

**分类型正确率：**

| | 单跳 | 多跳 | 不可回答 |
|---|---|---|---|
| 纯 LLM | 0.62 | 0.60 | **0.00** |
| RAG(BM25) | **0.80** | **0.27** | **0.94** |

### 这组数字讲了四件事

**① RAG 的核心价值被清楚量化了：幻觉率 1.0 → 0.056**

18 道语料里没有答案的题，纯 LLM **一道都没拒答**（全部编造）；加了检索和提示词约束后，
只有 1 道编了。**这是整组数据里最硬、最可复现的结论。**

**② 单跳题：0.62 → 0.80，检索确实有效**

**③ 多跳题：0.60 → 0.27，RAG 反而更差了**

这是最反直觉、也最有价值的发现。逐条诊断 80 道可回答题：

```
检索命中 且 答对       46
检索完全没命中          14      ← top_k=3 在这个语料上捞不到
检索命中 但 答错/漏答   20
```

多跳题需要**两段** gold 片段。BM25 用 `top_k=3` 从 1,919 个片段里同时捞中
两个特定片段，成功率很低；只捞到一段时，模型缺一半信息只能拒答或答错。
**结果就是：让它"凭记忆猜"（0.60）比让它"查资料但查不全"（0.27）还准。**

**④ 基线 0.61 偏高，是因为语料是模型"背过"的公开文档**

Vue 是大规模公开文档，模型训练时见过，所以不查资料也能猜对六成。
**这掩盖了检索的价值。** 真实企业场景的语料（内部文档、私有规范）模型没见过，
基线的 0.61 会大幅下降。

> **这是个方法论层面的坑：选语料时要意识到"模型先验知识"这个混淆变量。**
> 主动指出这一点，比报一个漂亮的数字更能体现严谨性。

### 下一步完全由数据驱动

| 发现 | 对应的改进 |
|---|---|
| 多跳召回不足（0.71） | **查询分解**：把一个多跳问题拆成两个子查询，分别检索（对应 `PROJECT_PLAN` 的 planner） |
| 词法通道有语义盲区 | **向量检索** + RRF 融合 |
| 检索命中但答错 20 条 | **rerank 精排** 候选集 |
| 基线虚高 | 换一份模型没见过的语料做对照 |

**每一行改进都有对应的数字支撑，不是"因为别人都这么做"。**

## 八、检索通道消融：三组对比（反直觉的结果）

把检索做成可切换的三种模式（`app/hybrid.py` 的 `mode` 参数），
同一套 98 道题、同一个模型、同一个判分器，只换检索通道：

| 指标 | **BM25（词法）** | 向量 | 混合（RRF） |
|---|---|---|---|
| 可回答题正确率 | **0.5875** | 0.4625 | 0.5500 |
| 片段召回率@5 | **0.7125** | 0.5687 | 0.7000 |
| 命中率@5 | **0.8250** | 0.6625 | 0.7875 |
| MRR | **0.7188** | 0.5396 | 0.6562 |
| nDCG@5 | **0.7270** | 0.5415 | 0.6627 |
| 单跳题正确率 | **0.80** | 0.68 | 0.78 |
| 多跳题正确率 | **0.2333** | 0.10 | 0.1667 |
| 单跳题召回 | **0.80** | 0.70 | 0.80 |
| 多跳题召回 | **0.5667** | 0.35 | 0.5333 |
| 拒答正确率 | 1.0 | 1.0 | 0.9444 |
| 幻觉率 | **0.0** | **0.0** | 0.0556 |

**结论：纯 BM25 全面胜出，纯向量最差，混合居中。** 11 项指标里 BM25 拿了 9 项第一，
而且是**一致地**领先，不是噪声。

**这和"应该做混合检索"的预期相反**，所以必须查清楚，不能就这么下结论。

### 排查过程

**假设 1：评测集偏"词法友好"（我的第一直觉）**

合成题是从文档原文生成的，我怀疑题目措辞和原文重合，导致 BM25 天然占优。

**实测推翻了这个假设**（脚本量的是"问题的词有多大比例直接出现在 gold 原文里"）：

```
single_hop   平均词法重合度 = 0.542   （重合度 ≥ 0.8 的占 24%）
multi_hop    平均词法重合度 = 0.282   （重合度 ≥ 0.8 的占  0%）
全部         平均词法重合度 = 0.444

对照——真实用户的改述型问法：
  重合度 0.000   「怎么让数据自动更新」
  重合度 0.000   「为什么我改了变量界面没反应」
```

**尤其多跳题：重合度只有 0.28（几乎不重合），BM25 却依然以 0.5667 vs 0.35 领先。**
如果原因是"题目贴原文"，多跳题应该反转，但它没有。

**假设 2（剩下的主要嫌疑）：向量模型太小**

用的是 `BAAI/bge-small-zh-v1.5` —— **bge 家族里最小的中文模型**（512 维 / 90MB）。
同系列还有 base（768 维）和 large（1024 维），生产环境常用 bge-m3（1024 维）。

选它是因为"本地、免费、下载快（96 秒）"，**代价就是检索质量**。

**假设 3：题型偏事实型**

评测题里大量是"某日期 / 某数字 / 某名称"，词法检索天生擅长这类；
而向量擅长的"概念型 / 主题型"问题占比不高。

> **手动验证支持这一点**：问「为什么我改了变量界面没反应」（纯改述，零词法重合）
>   - BM25 → 块 934（不相关）
>   - 向量 → 块 923「基于 Proxy 实现响应式的」✅
>
> **向量在改述型问题上确实更强，只是这类题在评测集里太少。**

### 这一轮真正的产出

**它没有证明"混合检索更好"，但它证明了另外三件更有价值的事：**

1. **建立了可切换的检索通道和可复现的消融流程** —— 换一个参数就能跑出三行对比数据
2. **用数据推翻了自己的假设**（评测集词法偏差），而不是直接采信直觉
3. **把"为什么向量没赢"收敛到了两个可验证的原因上**，下一步是换大模型重跑

**"我做了混合检索，效果更好"远不如这样有说服力：**

> "我做了混合检索，发现纯 BM25 反而更强。我先排查了是不是评测集的问题
> —— 实测题目与原文的词法重合度只有 0.44，多跳题只有 0.28，所以不是这个原因。
> 我又验证了改述型问题，向量确实能答对而 BM25 答不对。
> 所以问题出在 embedding 模型规模（512 维的小模型）和题型分布上，
> 下一步换 base/large 模型重测。"

### RRF 的一个已知特性（顺带发现）

观察 `app/hybrid.py` 的输出时注意到：一个**单通道排第 1、但没进另一通道前 20** 的片段，
RRF 得分只有 `1/(60+1) ≈ 0.0164`；而**两个通道都排 13 名**的片段能拿到 `2/(60+13) ≈ 0.0274`。

**结果是"两边都中等"经常压过"一边极好一边没有"。**

这是 RRF 的设计意图（奖励共识），但当两个通道强弱差距很大时，它会拖累强通道。
可调的方向：调小 `k`（让头部排名更占优势）、给通道加权、或增大每通道候选数。

## 九、换大模型后，结论翻转了

上面对比用的是 `BAAI/bge-small-zh-v1.5`（512 维 / **23M 参数**）。
怀疑是模型规模不足后，换成 `Qwen/Qwen3-Embedding-0.6B`（1024 维 / **596M 参数**，26 倍），
其余一切不变（同一套 98 题、同一模型、同一判分器、同一套 RRF 参数）。

### 结果：三个通道的排序完全变了

| 指标 | BM25（词法） | 向量 | 混合（RRF） |
|---|---|---|---|
| 可回答题正确率 | 0.5750 | 0.6125 | **0.6500** |
| 片段召回率@5 | 0.7125 | 0.7250 | **0.7438** |
| MRR | 0.7188 | 0.6521 | **0.7396** |
| nDCG@5 | 0.7270 | 0.6817 | **0.7666** |
| 单跳题正确率 | 0.80 | 0.80 | **0.86** |
| 多跳题正确率 | 0.20 | 0.30 | **0.30** |
| 单跳题召回 | 0.80 | 0.84 | **0.88** |
| 延迟 P50 (ms) | **862.8** | 1210.7 | 1472.5 |

**混合检索在三项核心指标（正确率 / 召回率 / MRR / nDCG）上全部第一。**

### 关键对比：同一个向量通道，只换模型

| 指标 | 小模型（23M） | **Qwen3（596M）** | 变化 |
|---|---|---|---|
| 可回答题正确率 | 0.4625 | **0.6125** | **+32%** |
| 片段召回率@5 | 0.5687 | **0.7250** | +27% |
| 命中率@5 | 0.6625 | **0.8125** | +23% |
| MRR | 0.5396 | **0.6521** | +21% |
| 单跳题正确率 | 0.68 | **0.80** | +18% |
| **多跳题正确率** | 0.10 | **0.30** | **+200%** |

**向量通道从"三项里最差"变成"超过 BM25"。**

### 所以第八节那个反直觉的结论，原因是这个

```
❌ 错误结论：在这个语料上，词法检索比向量检索更强
✅ 正确结论：23M 参数的小模型不足以支撑向量检索；
             换到 596M 参数后，向量反超 BM25，混合检索最优
```

**第八节的排查过程没有白做** —— 正是因为它排除了"评测集词法偏差"这个可能，
才把嫌疑锁定到模型规模上，才有了这次决定性的实验。

### 代价也要一并报出来

| 指标 | BM25 | 混合(Qwen3) | 代价 |
|---|---|---|---|
| 延迟 P50 | 862.8 ms | 1472.5 ms | **+71%** |
| 延迟 P95 | 1285.1 ms | 2085.0 ms | +62% |
| 入库耗时（1919 片段） | — | **766 秒** | 小模型只要 34 秒（**22 倍**） |
| 模型下载 | — | 2.38 GB | — |
| 幻觉率 | 0.0556 | 0.1111 | ⚠️ 18 个样本里 1 条 vs 2 条，在噪声范围内 |

**"混合检索更好"不是免费的：延迟 +71%，入库慢 22 倍，还要 2.4GB 模型。**
是否值得，取决于场景——这个权衡必须自己说出来，不能只报收益。

### 一句话总结这一轮

> 我先做出了"反直觉"的结果（BM25 赢），
> 然后**用数据排除了评测集偏差**，把原因锁定到模型规模，
> 换成 26 倍大的模型后**结论翻转**（混合检索最优），
> 并如实报告了它的代价（延迟 +71%）。

**这比一路顺利做出"混合检索最好"要可信得多 ——
因为它证明了我有能力判断一个结论什么时候不该信。**

## 十、查询分解：把多跳问题退化成单跳

倒数第二轮的数据把所有矛头指向同一处：

```
单跳题正确率  0.86     ← 已经不错
多跳题正确率  0.37     ← 唯一的坑
单跳检索召回  0.88
多跳检索召回  0.52     ← 瓶颈在检索，不在生成
```

原因很直接：多跳题需要**两段**资料，单次 `top_k` 检索要从 1,919 个片段里
同时捞中两个特定片段，成功率很低。

### 实现：两阶段（`app/planner.py`）

**阶段 1 · 分解**：LLM 把问题拆成 1~3 个自包含子查询，多路并行检索。

**阶段 2 · 补检**：把找到的资料交给模型，问它「还缺什么」，
用它的回答再检索一轮（由模型判断是否需要，不是固定加一轮）。

为什么需要阶段 2？因为多跳题里有一类是**桥接式**的，后半句依赖前半句的答案：

```
阶段 1 检索「澜芯 X1 由哪个团队开发」→ 找到"边缘计算团队"
此时才可能问出「边缘计算团队负责人毕业于哪所大学」
在阶段 1 之前，"该团队"指谁无从得知。
```

多路结果用 **RRF 再融合一次**（复用已有的 `rrf_fuse`）——
它本质上就是"融合多个排名列表"，至于这些列表来自不同通道还是不同子查询，它不关心。

### 结果：多跳题提升最明显

| 指标 | hybrid | **agent** | 变化 |
|---|---|---|---|
| 可回答题正确率 | 0.650 | **0.750** | **+15%** |
| 片段召回率@5 | 0.7438 | **0.8438** | **+13%** |
| nDCG@5 | 0.7666 | **0.8084** | +5% |
| MRR | **0.7396** | 0.7221 | −2% |
| 单跳：正确率 / 召回 | 0.82 / 0.88 | **0.86 / 0.90** | +5% / +2% |
| **多跳：正确率 / 召回** | 0.3667 / 0.5167 | **0.5667 / 0.7500** | **+55% / +45%** |
| 幻觉率 | **0.0556** | 0.1111 | ⚠️ |
| 延迟 P50 (ms) | **1147** | 3247 | **+183%** |
| 延迟 P95 (ms) | **1661** | 4676 | +182% |
| 单条 token | **614.6** | 868.0 | +41% |

**逐条对比（agent 相对 hybrid）**：

```
从错变对   9 条（多跳 6、单跳 3）
从对变错   1 条（单跳 1）
净收益    +8 条
```

**多跳题是最大受益者，而且基本没有副作用** —— 弄丢的那 1 条是单跳题。

### 完整演化链：每一步都有数字

| 指标 | BM25 | 混合·小模型 | 混合·Qwen3 | **+ 查询分解** |
|---|---|---|---|---|
| 可回答题正确率 | 0.575 | 0.55 | 0.65 | **0.75** |
| 片段召回率@5 | 0.7125 | 0.70 | 0.7438 | **0.8438** |
| nDCG@5 | 0.727 | 0.6627 | 0.7666 | **0.8084** |
| 单跳正确率 | 0.80 | 0.78 | 0.82 | **0.86** |
| **多跳正确率** | 0.20 | 0.1667 | 0.3667 | **0.5667** |
| 延迟 P50 (ms) | **863** | 874 | 1147 | 3247 |

**这张表就是"每一步改动带来多少收益、付出多少代价"的完整账本。**

### 代价与遗留问题（照实记）

| 代价 | 数值 |
|---|---|
| 延迟 | **+183%**（1147 → 3247 ms） |
| P95 延迟 | +182%（1661 → 4676 ms） |
| token 成本 | +41% |
| 幻觉率 | 0.0556 → 0.1111（18 个样本里 1 条 vs 2 条，**在噪声范围内，但方向不好**） |

**一个反直觉的现象：召回率涨了，MRR 反而降了**（0.7438 → 0.7221）。

原因是 RRF 融合的列表从 2 个变成了 4~6 个（原问题 + 子查询 + 补检），
**列表越多，正确答案越容易被"平均"到靠后的位置**。
这正是 RRF 那个已知特性的又一次体现（见第八节末）。

> **改进方向**：给原问题那一路更高的权重（加权 RRF），
> 让它作为"主查询"不被子查询稀释。这是一个可以用同一套评测直接验证的假设。

## 十一、上下文压缩：一次"自己挖坑自己填"的排查

查询分解之后，瓶颈从"找不到"变成了"给太多"：

```
片段召回率 0.8438    ← 该找的都找到了
单条 token 868       ← 但资料也多了
```

一次给模型 5~10 块资料（每块 300 字），真正包含答案的可能只有一两句。
**压缩的价值不是省 token，而是"用同样的预算看更多资料"。**

### 实现（`app/compress.py`）

用 LLM 做**抽取式压缩**：让模型从每块资料里挑出相关的**原文句子**（不改写、不总结）。

**为什么不用向量打分？** "切句 → 每句和问题算相似度 → 留高分句"听起来更工程化，但实测不可行：

```
一次查询要算约 50 个句子的向量
本机 Qwen3 每个向量约 300 ms（CPU 推理）
→ 光压缩就要 15 秒
```

一次 LLM 调用（约 0.8 秒）能同时处理全部资料，**反而快 20 倍**。
而且 LLM 能判断"这块虽然提到了关键词，但并没有回答问题"——向量相似度识别不了。

### 第一版：token 降 60%，但正确率掉了 12%

| 指标 | agent（无压缩） | **+ 压缩** | 变化 |
|---|---|---|---|
| 单条 token | 868.0 | **343.8** | **−60%** |
| MRR | 0.7221 | **0.7875** | +9% |
| 幻觉率 | 0.1111 | **0.0556** | 减半 |
| 可回答题正确率 | **0.750** | 0.6625 | **−12%** |
| 片段召回率@5 | **0.8438** | 0.7750 | −8% |

**精确率上去了，覆盖率下来了。**

### 排查：是"真丢了"还是"测量假象"？

压缩会丢掉部分句子，而检索指标靠"gold 片段能否逐字匹配"来算，
所以有可能是**句子被切碎导致匹配失败**（测量假象），而不是真的丢资料。

**逐条对比后确认是真丢了**：

```
召回上升  0 条
召回持平 72 条
召回下降  8 条      ← 且都是 1.0 → 0.0（整个片段彻底没了，不是匹配失败）
```

### 归因：坑是我自己挖的

翻回压缩提示词，第 4 条写着：

```
❌ 宁可少留，不要多留 —— 无关内容会干扰后续回答
                ↑ 我明确指示模型"激进地丢"
```

实际压缩率是 **10 块 → 3 块（丢掉 70%）**。模型只是**忠实地执行了我的指令**。

**而我的判断本身就错了**：
> 漏掉一句关键句的代价（问题直接答不出来），
> 远大于多留一句无关句的代价（稍微多点噪音）。

### 修法：把"激进"改成"保守"

```
✅ 宁可多留一句，也不要漏掉可能有用的一句。
   漏掉关键句子的代价，远大于多留一句无关句子的代价。
✅ 判断标准放宽：只要这句话**可能**和问题有关，就留下它。
   不要因为"不太确定"就丢掉。
```

压缩率随即从 **6.7% 放宽到 29%**，效果立刻变化：

| 指标 | 激进提示词 | **保守提示词** | 变化 |
|---|---|---|---|
| 可回答题正确率 | 0.65 | **0.75** | **+15%** |
| 拒答正确率 | 0.9444 | **1.0000** | +6% |
| **幻觉率** | 0.0556 | **0.0000** | **归零** |
| 片段召回率@5 | 0.8000 | **0.8187** | +2% |
| MRR | **0.7708** | 0.7125 | −8% |
| 单条 token | **356.5** | 498.3 | +40% |
| 延迟 P50 (ms) | **3881** | 4492 | +16% |

**改一段提示词：正确率 +0.10、幻觉率归零，代价是 token 涨 40%（但仍比不压缩低 43%）。**

### 验证"同样预算看更多资料"

保守压缩下，k=5 vs k=10：

| 指标 | k=5 | **k=10** |
|---|---|---|
| 可回答题正确率 | 0.7125 | **0.7500** |
| 幻觉率 | 0.0556 | **0.0000** |
| 片段召回率@5 | 0.8063 | **0.8187** |
| 单条 token | **426.8** | 498.3 |
| 多跳题正确率 | 0.5333 | **0.6000** |

**多给一倍候选、token 只多 17%，正确率和幻觉率都变好** ——
"压缩换预算"这个思路成立，只是收益温和。


**唯一变差的是延迟** —— 代价来自压缩/分解/自评这三次额外的 LLM 调用。

### 这一轮的三条经验

1. **提示词里的每一个倾向性措辞，都会变成系统行为。**
   "宁可少留"是我写的，模型只是照做。**指标异常时，先回去看自己写了什么。**

   6.7% 压缩率 → 正确率掉 12%；29% 压缩率 → 正确率追平且幻觉归零。

3. **区分"真丢失"和"测量假象"是排查的前提。**
   如果当时误判成"gold 片段只是被切碎了、模型其实看到了"，
   就会去改指标口径，而不是去修那个真正有问题的提示词。

## 十二、统计显著性：哪些结论真的站得住

加权 RRF 的消融结果很难看——不同配置的正确率在 ±0.03 之间乱跳，而且互相矛盾
（正确率最高的配置幻觉率最差）。这逼着我停下来问一个问题：

> **这些差异到底是真实效果，还是随机波动？**

### 先算评测集的"分辨力"

98 道题（80 道可回答 / 18 道不可回答）能分辨多大的差异？

| 指标 | 观测值 | 样本量 | 标准误 | 95% 置信区间 |
|---|---|---|---|---|
| 可回答题正确率 | 0.750 | 80 | 0.048 | [0.655, 0.845] |
| 单跳题正确率 | 0.860 | 50 | 0.049 | [0.764, 0.956] |
| **多跳题正确率** | 0.600 | **30** | **0.089** | **[0.425, 0.775]** |
| 片段召回率 | 0.819 | 110 | 0.037 | [0.747, 0.891] |
| 幻觉率 | 0.000 | **18** | — | **[0, 0.167]**（三倍法则） |

**样本量的代价很直观：多跳题只有 30 道，置信区间宽达 ±0.175。**

### 关键：必须用配对检验，不能用独立双样本

我第一版算错了 —— 用了**独立双样本**的公式，结论是"所有改动都不显著"。

**但我们两次评测跑的是同一批 98 道题，只是配置不同。这是配对数据。**
用独立公式会把"题目难度差异"当成噪声，而配对设计里它已经被消掉了。

配对数据的正确做法是看**不一致的对**：

```
b = 之前错、现在对    （改动救回来的）
c = 之前对、现在错    （改动弄丢的）
在"改动无效"的原假设下，b ~ Binomial(b+c, 0.5)
→ McNemar 精确检验
```

### 结果：只有一个改动是统计确证的

**全部 80 道可回答题：**

| 对比 | 救回 / 弄丢 | p 值 | 判定 |
|---|---|---|---|
| BM25 → 混合检索 | 8 / 2 | 0.1094 | 不显著 |
| 纯 LLM → RAG(BM25) | 14 / 17 | 0.7201 | 不显著 |
| **混合检索 → 查询分解** | **9 / 1** | **0.0215** | **显著 ✅** |
| 查询分解 → 激进压缩 | 4 / 12 | 0.0768 | 不显著（方向明确变差） |
| 激进压缩 → 保守压缩 | 12 / 4 | 0.0768 | 不显著（方向明确变好） |
| 保守压缩 → 加权 RRF | 7 / 4 | 0.5488 | **不显著** |

**多跳题（30 道）：**

| 对比 | 救回 / 弄丢 | p 值 | 判定 |
|---|---|---|---|
| 纯 LLM → RAG(BM25) | **0 / 12** | **0.0005** | **显著 ✅** |
| **混合检索 → 查询分解** | **6 / 0** | **0.0312** | **显著 ✅** |
| 查询分解 → 激进压缩 | 3 / 7 | 0.3438 | 不显著 |
| 激进压缩 → 保守压缩 | 7 / 2 | 0.1797 | 不显著 |
| 保守压缩 → 加权 RRF | 3 / 3 | 1.0000 | 不显著 |

### 修正后的结论

**站得住的（统计显著）：**

1. **查询分解有效** —— 整体 p=0.0215，多跳 p=0.0312（**多跳 6 条救回、0 条弄丢**）
2. **RAG 会破坏多跳题** —— 多跳 0 条救回、12 条弄丢，p=0.0005
   （这是"多跳检索不足"的铁证，也解释了为什么当初 RAG 的多跳正确率反而低于纯 LLM）

**站不住的（在噪声范围内）：**

1. ~~加权 RRF 能修 MRR~~ —— **p=0.5488，多跳 p=1.0000，完全无效。假设被推翻。**
2. ~~"召回涨了但 MRR 降了"是 RRF 稀释导致的~~ —— MRR 在 0.71~0.77 之间随配置随机跳动，
   当初那个"下降"很可能只是噪声。**我用一个噪声现象推导出了一个不存在的因果。**
3. 混合检索 vs BM25（p=0.1094）—— 方向对，但样本量不够，需要约 2 倍题目才能确认
4. 压缩的两步调整（p=0.0768）—— 方向很明确（4/12 变差、12/4 变好），但没到显著线

**确定性的（不涉及抽样，无噪声）：**

- **token 868 → 498（−43%）** —— 这是数出来的，不是估出来的
- **入库耗时、延迟** —— 同理

### 这一轮的三条教训

1. **98 道题只能分辨约 0.10~0.14 的正确率差异。**
   小于这个数的一切对比都在读噪声。**报数字必须同时报样本量。**

2. **配对数据必须用配对检验。**
   同一个实验用独立双样本公式会得出"全都不显著"，
   用 McNemar 能识别出真实效果。**方法选错，结论完全相反。**

3. **不要用噪声现象推导因果。**
   "召回涨了 MRR 降了"看起来像个因果链，我甚至给它编了个 RRF 稀释的机制解释，
   还专门去实现了加权 RRF —— **结果全是噪声。**
   遇到反直觉的小幅波动，先算它是不是噪声，再决定要不要归因。

## 十三、判分器人工校准：kappa = 0.616，但分歧的性质比数字重要

### 为什么要做

前面所有数字（正确率 0.75、幻觉率 0.0……）**都建立在一个没被验证过的 LLM judge 上**。
只报 judge 给出的分数、却不校验 judge 可不可信，是 LLM 评测里最常见的方法论漏洞。

### 怎么做的（四个关键设计）

**1. 分层抽样，刻意多抽"judge 判错"的**

按 78:20 的真实比例随机抽 30 条，只会抽到约 6 条判错项，kappa 极不稳定。
所以抽**全部 20 条判错项 + 12 条判对项**，共 32 条。

**2. 工作表不显示 judge 的判定（盲标）**

先看 judge 说了什么再标，人会不自觉地往那个结论靠，
算出来的 kappa 就成了自我实现的预言。

**3. 用【已有的报告】算 kappa，绝不重跑评测**

```python
# ⚠️ LLM 有随机性。重跑一遍会得到不同的回答和判定，
#    人工标注的那 32 条就对不上了 —— 算出来的 kappa 毫无意义。
#    必须用标注时看的那一份报告。
```

**4. "不确定"的条目不强行二值化**

32 条里有 1 条标注人写了「搞不清楚文档里有没有示例」。
**硬填一个值等于往数据里注入噪声**，所以直接排除，实际参与计算 31 条。

### 结果

```
参与计算      : 31 条
原始一致率    : 80.7%   （judge 判对 12 / 人工判对 16）
Cohen's kappa : 0.6157
结论          : 可用，但报告里必须说明局限

按题型拆开：
  multi_hop     n=16   一致 12/16 = 75.0%
  single_hop    n=11   一致  9/11 = 81.8%
  unanswerable  n=4    一致  4/4  = 100.0%
```

> **后续版本说明（2026-10-08）**：上面的 κ=0.6157 是早期报告与 31 条有效人工标签的结果，
> 不能代表当前判分器。最新 v12/v13 快照在 31 条标签上的 κ 分别为 0.3487 和 0.2821，
> 一致性偏低。当前 README 因此把质量指标标为探索性结果，并把 rubric 和扩大人工标注列为后续工作。
> 原始快照见 [`backend/eval/benchmarks/`](../backend/eval/benchmarks/README.md)。

**kappa 只有 0.616，落在"可用但要说明局限"这一档。**

### 但逐条看分歧，原因不是"judge 不可靠"

6 条分歧分成三类：

| 类型 | 条数 | 例子 | 谁对 |
|---|---|---|---|
| **拒答但答案已出现在回答里** | 2 | `sh-038`：系统说"无法回答"，但回答里**逐字复述了**标准答案 `this.answer = 'Error! ...' + error` | **judge 偏严** |
| **多跳只答对一半** | 3 | `mh-020`：第一问对（Vue 对象 ✅），第二问答成"基于类型声明"（标准是"运行时声明"） | **人工偏宽** |
| **人工看漏** | 1 | `mh-028`：系统答"Proxy；.prevent"，与标准完全一致，judge 判对，人工标了错 | **judge 对** |

**所以 kappa 低的真正原因是：「正确」这个词没有可操作的判定标准。**

```
judge 的标准 : 是否【明确给出】标准答案的核心事实
人工的标准   : 系统是否【努力了、方向上对】（隐含）
```

**两方用了不同的尺子，不是判分器坏了。**

### 三个实际影响

**① 判分器整体偏严 → 我们报出的正确率是保守下界**

2 条"拒答但引出答案"里，judge 判错而人工判对。
**方向是安全的**：真实正确率只会比 0.75 高，不会低。

**② 多跳题的分歧最集中（75% 一致）→ 判分器在多跳上最不可靠**

原因也清楚：多跳题有**两个**要点，答对一半该怎么算，judge 和人的尺度差最多。
**所以多跳题的数字（0.60）要打折看待。**

**③ 顺带发现一个真实系统问题：模型太保守**

2 条"拒答但答案就在回答里"的案例说明：
**系统找到了答案、甚至在回答里复述了，却不敢下结论。**
提示词里「资料不足就直接回答无法回答」这条可能约束过紧。

> **改进方向**：在提示词里补一句"如果资料中已出现答案，即使你觉得不完整，
> 也要先给出它，再说明不确定的部分"。

### 这一轮的价值

**kappa 0.616 不是个漂亮的数字。但"知道它为什么低、以及偏低的方向是保守的"，
比一个没有校准过程的 0.9 更可信。**

可以直接这样讲：

> "我对 judge 做了人工校准：分层抽 32 条盲标，kappa 0.616。
> 我又逐条看了 6 条分歧，发现不是 judge 不可靠，而是两方对'正确'的判定标准不一致——
> judge 按'是否明确给出核心事实'，人工按'方向上对不对'。
> 而且 judge 偏严的那 2 条是系统找到了答案却没敢下结论，
> **说明我报出的正确率是保守下界**，同时暴露出提示词约束过紧这个真实问题。"

**这比报一个没校准过的漂亮数字强得多 —— 因为它证明我知道自己的数字什么时候不可信。**

## 十四、修判分器：一个把好回答判成幻觉的规则

### 怎么发现的

改完提示词后评测：**正确率 0.75 → 0.85**，但**幻觉率 0.0 → 0.1667**。

看起来是个典型的权衡（答得更多 = 编得更多）。但逐条看那 3 条"新幻觉"，
发现只有 1 条是真的：

| id | 新回答 | 判定 |
|---|---|---|
| `un-014` 问「ref 的 getter 应该只做什么」 | 「getter 的职责应该仅为计算和返回该值」——**资料里说的是「计算属性」的 getter**，被套到了 `ref` 上 | **真·张冠李戴** ❌ |
| `un-015` 问「大于 `Number.MAX_SAFE_LIMIT` 的值」 | 「对于大于 `Number.MAX_SAFE_INTEGER` 的值…不准确。**资料中出现的常量名是 `MAX_SAFE_INTEGER`，而非问题中所写的 `MAX_SAFE_LIMIT`**」 | **这是更好的回答** ✅ |
| `un-016` 问「非 `<slot-frame>` 节点」 | 「非 `<template>` 节点被视为默认插槽内容。**注：你问题中写的是 `slot-frame`，而资料原文是 `template`**」 | **同样更好** ✅ |

**后两条明确指出了"问题里的实体在资料中不存在"，然后给出了资料里真实存在的信息。**
这是知识库问答最理想的回答方式，不是编造。

### 根因：判分规则太粗

```python
# 旧规则
1. refused=true 表示系统明确表达了"资料不足、无法回答、未提及"。
2. 只要系统给出了具体的事实性答案（哪怕语气不确定），就应判 refused=false。
```

规则 2 把「给出了任何具体答案」等同于「编造」。**但幻觉的定义应该是"把资料里没有的内容当事实陈述"，而不是"是否给出了具体答案"。**

### 修法

```python
"""refused=true 表示系统没有编造事实。下面两种情况都算：
     1. 明确表示"资料不足 / 无法回答"。
     2. 指出了问题里的关键实体在资料中不存在，并且只陈述了资料里
        实际存在的信息。**这是更好的回答，不是幻觉。**

   refused=false 仅当系统把资料里没有的内容当作事实陈述出来。

   【最容易判错的地方】
     系统说"资料里没有 X，但资料里有 Y"，且 Y 确属资料内容
         → refused=true（它诚实，且没编造）
     系统直接把 Y 当成 X 的答案讲出来，不说明两者不是一回事
         → refused=false（张冠李戴，属于编造）

   判定标准是【有没有把资料里没有的内容当事实陈述】，
   不是"有没有给出具体答案"。"""
```

### 验证：改动是精确的，不是全局放松

改完之后**不能重跑系统**（LLM 有随机性，回答一变就分不清是判分器改的还是回答变了），
所以写了 `eval/rejudge.py` —— **拿同一批已落盘的回答，只把判分这一步重跑**，
变量只有一个。

把 14 份历史报告全部用新尺子重判，**总共只有 4 条判定发生变化**：

| 报告 | 变化条数 | 幻觉率 |
|---|---|---|
| `v6-vector` | 1 | 0.0556 → **0.0** |
| `v6-hybrid` | 1 | 0.1111 → **0.0556** |
| `v12-prompt` | **2** | 0.1667 → **0.0556** |
| 其余 11 份 | 0 | 不变 |

**只有 4 条变化，说明修的是那个特定模式，不是把尺子整体泡软了。**
（如果改动导致几十条翻转，那才是"放松标准"的危险信号。）

而 `v9`（旧提示词，幻觉率本来就是 0）重判后 **0 条变化** —— 一致性检查通过。

### 修正后的完整演化链

所有报告都用同一把尺子重判过：

| 指标 | 混合·Qwen3 | +查询分解 | +激进压缩 | +保守压缩 | **+改进提示词** |
|---|---|---|---|---|---|
| 可回答题正确率 | 0.65 | 0.75 | 0.65 | 0.75 | **0.85** |
| 拒答正确率 | 0.9444 | 0.8889 | 0.9444 | **1.0000** | 0.9444 |
| 幻觉率 | 0.0556 | 0.1111 | 0.0556 | **0.0000** | 0.0556 |
| 片段召回率@5 | 0.7438 | **0.8438** | 0.8000 | 0.8187 | 0.8313 |
| MRR | 0.7396 | 0.7221 | **0.7708** | 0.7125 | 0.7129 |
| 单跳正确率 | 0.86 | 0.86 | 0.78 | 0.84 | **0.92** |
| **多跳正确率** | 0.30 | 0.5667 | 0.4333 | 0.60 | **0.7333** |

**配对检验（保守压缩 → 改进提示词）：**

```
可回答题     救回 10 / 弄丢 2   p=0.0386   显著 ✅
不可回答题   救回  0 / 弄丢 1   p=1.0000   不显著
```

**净收益：可回答题 +10，不可回答题 −1 → 净 +9 条。**

而且提升是**两种题型都有**：单跳 0.84 → 0.92，多跳 0.60 → 0.7333。

### 代价

| | 保守压缩 | 改进提示词 |
|---|---|---|
| 单条 token | 498 | **672**（+35%） |

答案更长（模型现在会把"找到的部分"都说出来），token 成本上升。

### 这一轮的两条经验

**1. 度量定义错了，所有对比都是在错误的基础上做的。**

幻觉率从 0 涨到 0.167 的时候，第一反应是"提示词改坏了"。
但如果不逐条看那 3 条，就会**把"幻觉率 16.7%"写进报告——白白抹黑自己做出来的东西**。

**2. 改度量之后必须能"只重判、不重跑"。**

LLM 有随机性，重跑系统就分不清数字变化是判分器改的还是回答变了。
所以写了 `eval/rejudge.py`：拿同一批落盘回答，只重跑判分。
**这样变量只有一个，结论才干净。**

## 十五、延迟优化：把「自评」和「压缩」合并成一次调用

### 先测量，再动手

延迟归因显示 **71% 的时间花在三次辅助 LLM 调用**上：

```
端到端 P50 = 4692 ms
  ├─ compress.context     1407 ms   30%   ← 最大单项
  ├─ retrieve.round1      1631 ms   35%
  ├─ llm.stream            967 ms   21%
  ├─ planner.decompose     785 ms   17%
  ├─ planner.assess        784 ms   17%
  └─ retrieve.round2       662 ms   14%
```

我原来的计划是"并行化多路检索" —— **那只动得到检索那部分**。
测量把这个方向纠正了。

### 关键测量：补检到底触发多频繁

合并只在"资料够、不用补检"时省一次调用。所以先测频率：

```
16 道多跳题里：
  assess 被调用的          16/16
  触发了补检（round2）的     3/16  = 19%

→ 81% 的情况里，assess 说"资料够了"，
  然后紧接着又要为压缩再调一次模型 —— 这两件事完全可以一次问完。
```

### 受控 A/B（同一批检索结果，只换调用方式）

```
分开：assess        756 ms
分开：compress     1909 ms
分开：合计         2665 ms
合并：assess+compress  1396 ms
                   ────────────
省下               1269 ms（48%）
```

> **注意合并版的调用本身比单独 assess 慢**（1396 vs 756）——
> 因为它要多输出抽取出来的句子。
> 所以省的是"一次往返的钱"，不是白赚。

**单次样本的延迟读数毫无意义。**

## 十六、一个会静默污染所有实验的坑：Windows 上杀不干净 uvicorn

### 现象

改完代码、重启后端、跑冒烟测试 —— **发现走的是旧代码路径**。
查了半天才发现：

```
端口 8000 被 PID 58000 占用
  → 但 PID 58000 已经不存在了
  → 真正占着端口的是它的【multiprocessing 子进程】PID 66948
```

**uvicorn 在 Windows 上会 spawn 一个 multiprocessing 子进程来干活。**
按端口杀进程时杀掉的是父进程，**子进程还活着，继续用旧代码服务**。

### 危害

**"重启后端"看起来成功了（端口检查显示已释放），实际跑的仍是旧代码。**
你会在错误的代码上做测量、得出错误结论，而且完全没有报错提示。

### 修法：加一个代码版本标记

```python
def _code_version() -> str:
    """当前进程实际加载的代码版本（按 app/*.py 的最后修改时间算）。"""
    app_dir = Path(__file__).resolve().parent
    latest = max((p.stat().st_mtime for p in app_dir.glob("*.py")), default=0.0)
    return datetime.fromtimestamp(latest).strftime("%m-%d %H:%M:%S")

# /api/health 返回里带上它
```

重启后第一件事就是核对：

```powershell
# 磁盘上最新代码的修改时间  vs  进程报告的 code_version
# 不一致 → 旧进程还活着，测量作废
```

### 教训

> **在一个「改代码 → 重启服务 → 测量」的循环里，
> 必须先确认"服务真的加载了新代码"。**
> 否则你会在旧代码上做实验，而所有检查都显示一切正常。

这类"静默失效"比报错更难查 —— 因为它不报错。
